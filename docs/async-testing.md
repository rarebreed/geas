# Asynchronous Testing

Just like a regular microservice, there are often parts of testing which can take an indeterminate amount of time.
There might be some part of your code that is dependent on some other task which may or may not be complete yet.

The traditional solution for testing has been problematic in many aspects.  Here are what I call the Fallacies of Test

1. The functionality to test is synchronous and blocking (and therefore quick)
    a. Corrollary: all dependencies of the functionality to test are synchronous and quick
2. A test should complete in a minute or less
    - this follows from rule 1
3. The functionality to test is stateless (eg, REST services)
    a. Corrollary: dependencies of the functionality to test is stateless
    b. Corrollary: the order that you make use of functionality does not matter because it is stateless
4. Tests are stateless
    - Corrollary: tests can run in any order
    - Corrollary: tests can run in parallel

So why are these _fallacies_?

- End to end testing is the norm unfortunately
- It often assumes the component under test is synchronous and ready for test
- A feature can be contained as test cases in a suite, but:
    - Test cases are designed as monolithic entities that run all in the same invocation
        - It is usually frowned on for one test case or test method to depend on another
        - IOW, a test case or method should not care about ordering, but this is not always realistic
    - Most testing assumes all the ducks are lined up and ready to go
        - should a dependency failure be a test failure?
        - Often it is difficult to even know when you _can_ test

And tests are only half the battle, perhaps less than half.  A significant portion of testing is building out the test
data and other infrastructure for the tests to even run.  Generating test data can become more difficult than the
assertion of the test.  

## Putting it all together

As we can see from the above, we can have several problems with tests 

- The system under test may have tasks that take a long time to complete
- The test itself may have tasks that are async, or take a long time to complete
- Tests can contain multiple tasks, some of which depend on each other or on system dependencies
- Most tests do not keep track of dependency state because they assume everything is ready
- Test data itself may take a long time to become ready

Validation that the system is even ready for test can also be very difficult if everything is treated as if it was a
synchronous and/or stateless world

## It's an async world

The problem is that pretty much everything is asynchronous, and there isn't an entity that drives and orchestrates the
data flow and processing. Testing needs to move to an event driven architecture much like a microservice.

Microservices are the new norm, where a smaller service handles some aspect of data processing.  One microservice
might depend on work done by another microservice.  And yet a third needs the output of both. Microservices typically 
do not directly invoke other services.  Instead, they are decoupled from each other, but send event data to a message
bus.  Other services which are interested in the events of a service can subscribe to the bus and get the event.  For 
example, that some state changed, or a process completed, and depending on the event, perform some action.

What makes async hard is that like multithreaded programming, there is no guaranteed order in which some event will be
completed.  Synchronous programming is easy to reason about, but can waste huge amounts of time if there is other work
that could be done.

## Thinking of dependencies and events

This means you must think about your problem based on dependencies.  When you can break down your problem into tasks
that clearly define their dependencies, not only does it become clear how failures can cascade, but it also allows for
optimizing code to run concurrently, or even in parallel.

If task B needs information that was generated by task A, you have no choice but to wait for task A to finish for B to
do its work.  However, who is to say that A and B have to run in the same program?  In a monolithic architecture (and
that includes most testcases now), task A and B will run inside the same application/test/service.  In a microservice or
EDA model, task A and B are separate processes, possibly running on another machine across the network, another thread
in the same memory space, or a separate process on the same process talking over a messaging channel.

If task A is allowed to run independently, then it will have the data needed for task B already done, because task A was
running independently.

It is the events that a service or task generates that are the dependencies for downstream tasks.

## It's a serverless world

Quite a bit of today's architecture has moved to a serverless or at least a managed service (ie, EMR, Glue Jobs, or Step
Functions).  In a serverless architecture, there are two key concepts:

1. You don't have to think of managing the servers that manage your service 
   - load balancing
   - rate limiting
   - image management for AMI
2. You break up your services into functions (a lambda is an anonymous function in lambda calculus)

So in a serverless oriented architecture, think of the functions that will be needed to do what your service does, and
how those functions need to interact with each other.  For example, you may have three separate functions that handle
some different aspect of the application which:

- Run at different times
- at different cadences
- but all three functions need to run for some Work to be completed 
- and the three may all need to coordinate with each other (read or update some data)

## It's a Jenkins world (in testing)

For many (most?) companies, Jenkins is the way that tests are executed.  Jenkins was initially designed as a kind of
crontab that could execute a task on a schedule.  Later, jobs could trigger other jobs, and pipelines were added that 
could break up a `Job` into separate stages that could conditionally run.

In a lot of ways, Jenkins can be thought of as a kind poor man's `serverless`.  You have a `Job` that performs one or
more tasks in its stages.  The problem with Jenkins are several:

- It has limited ways to trigger a Job (REST API, downstream/upstream jobs, webhooks and cron)
    - Some plugins extend this, like for example SQS messages or email, but they are not guaranteed
- Because of that, Jobs (and the pipelines they run) are often designed as monoliths
    - You can trigger downstream jobs, but often new stages are added instead
- A Jenkins Job has a maximum execution time (say for example one hour) that can easily be broken
    - If you are screaming that tests should take no more than a minute or two, you have never worked with Big Data

For example, although a pipeline is broken into stages (and can have parallel stages), they still run each stage 
sequentially.  If any stage fails, then you have to remember to use a `retry` block.  Also, we don't have a way to 
resume all the stages that passed previously.  This makes triaging difficult, and without a way to resume at only the
point of failure can be costly in time and resources (human and computing).

Architecturally speaking, a test may have dependencies that themselves are ready at different points in time. A specific
stage only care about one dependency, but another stage may need another dependency. So you need a way to know you are
even ready to test.  The only way Jenkins can make this happen is by running each dependency tracker on a cron, and 
maintaining a state table.  However this polling means we may waste valuable time.  For example, if your checker runs at
6pm but the dependency finished at 6:01pm, well, you have to wait almost 24 hours to even run your test.  

So, can we make Jenkins Jobs more like a microservice/EDA?  Yes!

### Jenkins Jobs as functions

Instead of treating a Jenkins Job as a pipeline of stages, each running some code which in turn may be monolithically
designed, we need to think of Jobs as self-contained Tasks.  Imagine pulling out each `stage` into its own Jenkins Job
which can be triggered independently.  How are they triggered independently?

As mentioned earlier, Jenkins has 4 basic ways to programmatically trigger a job.  We can make use of the REST API to
trigger a Jenkins Job.  So the next question is...who pulls the trigger?

The immediate answer is a lambda will.  So what triggers the lambda?  The lambda will be linked either to a rule on an
event bus, or a message from an SNS/SQS channel.  What triggers the event or transmits the message onto the channel is
how you design the data flow of your `Work`.
